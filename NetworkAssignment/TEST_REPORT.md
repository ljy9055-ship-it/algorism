# 게임 네트워크 프로그래밍 — 시험 기록

> UDP 수치는 이전 시험 화면에서 확인한 값, NGO는 사용자가 직접 수행하여 성공을 확인한 기능 시험을 기록했습니다. 측정하지 않은 수치와 재현 범위는 구분해 기재했습니다.

## 1. UDP 기능 시험

| 시험 대상 | 실행 조건·재현 순서 | 기대 결과 | 실제 결과·측정값 | 수정·조정 내용 | 다시 확인한 결과 |
|---|---|---|---|---|---|
| 두 피어 실행/양방향 위치 | 동일 PC에서 A: 9001, B: 9002 실행, 각각 W/A/S/D 입력 | 자기 위치만 변경, 상대 최신 위치 수신 | 양방향 통신 및 상대 위치 표시 성공(사용자 확인) | 입력 루프와 수신 루프 분리 | 성공 |
| 송신 피어 식별 | A와 B를 다른 ID로 실행, `P` 조회 | 상대 ID를 구분해 보관 | A/B 구분 및 상대 상태 표시 확인 | `peerId`, `remotePeerId` 사용 | 성공 |
| 오래된 번호 | 동일 피어 새 메시지 2개 보낸 뒤 `T` | 이전 번호 위치 적용 금지 | 오래된 번호 무시 동작 확인(사용자 확인) | `receivedSequence <= lastRemoteSequence` 검사 | 성공 |
| 중복 번호 | 새 메시지 후 `R` | 같은 번호 재반영 금지 | 중복 번호 무시 동작 확인(사용자 확인) | 같은 판정 규칙 | 성공 |
| 잘못된 메시지 | 송신 피어 `E` | 빈/형식/숫자/ID 오류 거절 및 계속 실행 | 메시지 거절 후 정상 통신 확인 | 형식·피어ID·숫자 검사 | 성공 |
| 수신 통계 분류 | B에서 `W`, `R`, `E` → A에서 `P` | 정상 1, 중복 1, 잘못된 5, 총 7 | **전체 7, 정상 반영 1, 무시 1, 잘못된 5** | `totalDatagrams` 카운터 추가 | **1+1+5=7 일치** |
| 접속 주소/포트 변경 입력 | 실행 시 기본 IP·포트 표시 및 Enter 적용 | 피어별 설정 가능 | 기본값 실행 후 통신 확인 | `ReadAddress`, `ReadPort` 추가; 누락된 `remotePeerId` 선언 수정 | 기본 설정 성공; 사용자 지정 비기본 주소 시험은 미실시 |
| 실행 중 포트 중복 | 이미 실행 중인 동일 피어 추가 실행 | 충돌 원인 확인 및 비정상 중복 실행 방지 필요 | `SocketException (10048)` 관찰 | 중복 프로세스 종료 후 A/B 각 1개 실행 | 정상 실행 확인 |

## 2. UDP 전송량 시험 — 각 조건 별도 실행

| 항목 | 100개 / 10ms 대기 | 1,000개 / 10ms 대기 | 1,000개 / 1ms 대기 | 1,000개 / 대기 없음 |
|---|---:|---:|---:|---:|
| 송신 시도 | 100 | 1,000 | 1,000 | 1,000 |
| 송신 성공 | 100 | 1,000 | 1,000으로 관찰됨 | 1,000 |
| 송신 오류 | 0 | 0 | 0으로 관찰됨 | 0 |
| 송신 경과 시간 | **1,066ms** | **10,628ms** | **약 16초** (화면에서 관찰; 정확한 값은 확인 필요) | **8ms** |
| 상대 정상 반영 수 | **100** | **1,000** | 미측정 | **1,000** (이전 대화에서 사용자 확인) |
| 전체 수신 데이터그램 수 | 당시 집계 기능 미구현 | 당시 집계 기능 미구현 | 미측정 | 당시 집계 기능 미구현 |
| 상대 오래된·중복/잘못된 메시지 | 0 / 0 | 0 / 0 | 미측정 | 미측정 |
| 수신 측 측정 소요 시간 | 미측정 | 미측정 | 미측정 | 미측정 |

### 관찰·해석

- 같은 10ms 대기 설정에서 100개를 보내는 데 1,066ms, 1,000개를 보내는 데 10,628ms가 걸렸습니다. 메시지 수가 10배 늘어 송신 반복 소요 시간도 약 10배 증가했습니다.
- 같은 1,000개 메시지에서 **10ms 대기 → 대기 없음**으로 변경하자 송신 반복 경과 시간이 **10,628ms → 8ms**로 감소했습니다. 송신 측 측정 구간의 경과 시간은 약 1,329배 차이 납니다. 이는 전체 네트워크 처리 완료 시간이나 수신 성능의 같은 배율 향상을 뜻하지 않습니다.
- `Task.Delay(1)` 조건은 약 16초로 관찰되어 10ms 조건보다 오히려 느렸습니다. 짧은 비동기 지연은 OS 스케줄러·타이머 해상도에 좌우되므로 정확히 1ms를 보장하지 않습니다. **이 값은 정확한 로그 숫자 재확인 전에는 근삿값으로만 사용**합니다.
- 이전 10ms 조건에서 상대 정상 반영 1,000개를 확인했습니다. 대기 없음 조건에서도 상대 정상 반영 1,000개를 사용자와 함께 확인했으나, 당시 `totalDatagrams` 집계는 아직 추가되지 않았습니다.
- 정상 반영 수가 송신 성공 수보다 적을 경우 이를 즉시 확정 손실로 단정하지 않습니다. 메시지 지연, 순서 역전(낮은 번호 무시), 관찰 시점 등에 따라 달라집니다. **송신 성공 수는 실제 수신 보장이 아닙니다.**

### 개선·조정 과정

1. 기본 프로그램의 양방향 수신은 동작하지만 문자열 출력만 수행 → 파싱·최신 위치 저장 및 표시 추가.
2. 이전/같은 번호 재전송 시험 불가 → `T`·`R` 도입 후 거절 동작 확인.
3. 잘못된 메시지 시험 불편 → `E` 추가 후 프로그램 계속 작동 확인.
4. 전송량 시험 코드 추가 중 같은 스코프의 `message`, `data` 변수명 충돌(`CS0136`) → `bulkMessage`, `bulkData`로 변경 후 정상 실행.
5. 수신 카운터 구분 미흡 → `totalDatagrams`, `receivedCount`, `ignoredCount`, `invalidCount`로 분리 후 7개 수신 분류 시험 성공.
6. 1ms 간격 변경은 시간 개선이 없어, 별도 대기 없는 조건으로 추가 조정 후 8ms 송신 결과 측정.

## 3. NGO 기능 시험 — 수행 및 사용자 확인

기본 환경: Unity Editor **6000.6.6f1**(Host) + 같은 PC의 Windows 빌드(Client), 접속 설정 `127.0.0.1:7777`, 씬 `CoinGameScene`(실제 이름 최종 확인). 점수는 공동 점수이며 코인은 10개입니다. 아래의 "성공"은 사용자가 실행 후 기능 작동을 확인한 뜻이며, 별도로 캡처되지 않은 서버 로그 문구·밀리초 단위 시간은 실측값으로 꾸미지 않았습니다.

| 시험 대상 | 실행 조건·재현 순서 | 기대 결과 | 실제 결과·측정값 | 수정·조정 내용 | 다시 확인한 결과 |
|---|---|---|---|---|---|
| Host/Client 접속 | Editor Play → Host 시작, Windows 빌드 실행 → Client 시작 | 두 참여자 접속 및 각 플레이어 생성 | 두 실행 프로그램 동시 접속·플레이어 생성 성공(사용자 확인) | `NetworkManager`, Player 프리팹 설정 | 성공 |
| 본인 플레이어 입력·이동 | 양쪽 각각 Game 화면 활성화, WASD 이동 | 본인 플레이어만 조작 | CharacterController 이동 성공 | 기존 `Input.GetAxisRaw`와 New Input System 설정 불일치 → `Active Input Handling = Both` | 성공 |
| 상대 화면 이동 동기화 | Host와 Client 각각 이동, 상대 화면 확인 | 동일 플레이어 이동이 다른 화면에도 반영 | 양방향 이동 동기화 성공(사용자 확인) | 소유자 권한 NetworkTransform 사용, 빌드 재생성 | 성공 |

| Client 종료·재접속 | 공동 점수 3에서 Client 종료 → Host가 1개 더 획득 → Client 재접속 | Host 유지; 재접속 Client 현재 점수·코인 상태 수신 | **공동 점수 4, 남은 코인 6개**로 양쪽 상태 일치(사용자 확인) | 서버 쓰기 상태 동기화 | 성공 |
| 접속 상태/실패 후 재시도 | Host 없이 Client 연결 시도, 종료·재시도, 정상 Host 재접속 | 접속 시도/성공/종료/실패 메시지와 재시도 가능 | UI 동작 성공(사용자 확인) | NGO 콜백 및 10초 연결 타임아웃 추가 | 성공 |

### NGO 시험의 범위·제한

- F5는 **사람이 두 실행 창에서 연속으로 누른** 경쟁 요청 시험입니다. 진정한 동시 처리의 부하 시험으로 쓰지 않습니다. 다만 서버가 상태를 단일 순서로 판정하면서 중복 보상을 막는 것을 관찰했습니다.
- 거리 초과 판정은 서버가 동기화받은 Player 위치에 기반합니다. **악의적 Client가 자기 위치를 임의 변경하는 경우를 막는 서버 권한 위치 검증은 미구현**이며, 설계상 한계입니다.
- 테스트 시 실제 서버 로그를 파일로 별도 추출하지는 않았습니다. 최종 제출 전에 가능하면 Host Console 로그와 양쪽 화면을 캡처하여 `TEST_REPORT.md`와 함께 보관하세요.

## 4. 조정 전후 비교 및 해석

- **필수 전후 비교:** UDP 1,000개 동일 메시지에 대해 10ms 대기에서 **10,628ms**, 대기 없는 조건에서 **8ms**가 걸렸습니다. 두 조건에서 상대 위치의 정상 반영 수는 각각 **1,000개**로 확인되었습니다. 같은 형식·같은 메시지 수를 사용한 *송신 구간 시간* 비교이며, 전체 왕복 지연이나 수신 처리 시간을 측정한 결과는 아닙니다.
- UDP 1ms 대기 시험은 약 16초로 관찰되어 10ms보다 더 오래 걸렸습니다. OS 타이머/스케줄링 영향을 설명하는 관찰 사례이며 확정적인 원인을 계측해 증명하지는 않았습니다.
- 각 조건의 **전체 수신 데이터그램 수는 대량 송신 당시 미집계**였으므로 뒤늦게 1,000개로 기입하지 않았습니다. 후속 소규모 오류 시험에서 `7 = 정상 1 + 무시 1 + 오류 5`로 정확히 분류되는 것을 확인했습니다.
